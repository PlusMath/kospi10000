# KOSPI10000 vscore P1 설계안 (미구현 — 설계 문서만)

> 이 문서는 `claude-code-vscore-improvement-prompt.md`(2026-08-27 P0 작업 지시서)의 "P1 설계안"
> 절에서 요청된 내용을 정리한 것이다. **P0 작업에서는 여기 적힌 어떤 것도 구현하지 않았다** —
> 코드 변경은 전부 [attractiveness-scoring-spec.md](./attractiveness-scoring-spec.md)의
> "2026-08-27" 변경 이력에 기록된 것(배당 파서, fpe 0점 처리, coverage 게이트, 등급 명칭,
> `data/fundamental_score.json`)뿐이다. 이 문서는 다음 세션이 P1을 실제로 계획할 때 출발점으로
> 쓰라고 남겨두는 것이다.

## 1. 가치/품질/성장 점수 분리

현재 vscore는 6개 지표(Forward PER/PBR/배당수익률/ROE/EPS성장률/재무안전성)를 하나의 가중합으로
섞는다. P1에서는 이를 3개 하위 점수로 분리하는 것을 제안:

| 축 | 후보 지표 | 근거 |
|----|-----------|------|
| Value | NTM earnings yield(1/Forward PER), B/P(1/PBR), EV/CFO 또는 FCF yield | 현재 Forward PER/PBR과 상당 부분 겹치지만, EV/CFO·FCF yield는 회계상 이익 조작 여지가 큰 순이익 대신 현금흐름 기준이라 왜곡에 덜 취약 |
| Quality | TTM ROE 또는 ROIC, 현금전환율(CFO/순이익), 레버리지(부채비율 등), 5년 이익변동성 | 현재는 ROE·재무안전성만 봄 — 이익의 "질"(현금 뒷받침 여부)과 "안정성"(변동성)이 빠져있음 |
| Growth | 3년 매출/EPS CAGR, 이익추정치 수정 방향(컨센서스 상향/하향) | 현재 EPS성장률은 3개년 단순 변화율(사실상 YoY 근사)이라 구조적 성장 추세와 일회성 요인을 구분 못함 |

**설계 방향**: 각 축을 현재와 동일한 percentile 기반 가중합으로 산출하고, 최종 vscore는 3축의
단순 평균이 아니라 (P1 마지막 항목의) 표준화 결합을 거친 값으로 제시. 3축을 각각 카드에
노출하면(예: "가치 72 · 품질 58 · 성장 81") 사용자가 "싸지만 질이 낮은지 / 비싸지만 질이
좋은지"를 구분할 수 있어 현재의 단일 숫자보다 정보량이 많음.

**전제 조건**: EV/CFO, FCF yield, ROIC, 현금전환율은 현재 파이프라인이 파싱하는 사업보고서
"연간 재무데이터" 블록(순이익/자본총계/부채총계/EPS 3개년)에 없는 항목(영업활동현금흐름,
투자활동현금흐름, 유형자산 등)이 필요 — 아래 4번(OpenDART XBRL) 없이는 착수 불가.

## 2. 업종별 별도 모델

현재는 6개 지표를 모든 업종에 동일 가중치(25/20/15/15/15/10)로 적용하고, 금융업만 재무안전성을
예외 제외하는 단일 규칙이 있다. 실제로는 업종마다 밸류에이션 관행이 다르다:

- **금융/보험/증권**: PBR·ROE 중심(이미 부분 반영), 배당수익률 가중치를 올리는 게 더 적합할 수 있음.
- **지주회사**: NAV(순자산가치) 대비 할인율이 핵심인데 현재 지표엔 없음 — 자회사 지분가치 합산
  필요(외부 데이터 소스 없이는 산출 불가).
- **바이오/제약(임상 단계)**: 이익이 구조적으로 없어 PER/ROE가 무의미 — 현재도 이런 종목은
  `fpeLoss`/`missing`으로 자연스럽게 빠지지만, "성장성만으로 평가"하는 대체 축이 없어 아예
  점수가 안 나오는 경우가 많을 것으로 추정(실측 필요).
- **경기민감(철강/화학/조선 등)**: 사이클 저점에서 PER이 왜곡(이익 급감으로 분모가 작아져 PER이
  오히려 치솟는 현상)되는 걸 감안해 PBR·EV/EBITDA 비중을 올리는 게 관행.

**설계 방향**: `$scoreMetricDefs`를 업종군별로 별도 배열로 두고(현재 금융업 제외 로직을 일반화),
가중치 프리셋을 `$scoreMetricDefsByIndustryGroup['금융·은행·증권'] = @(...)` 형태로 확장. 임의
병합(현재의 `$scoreIndustryGroupMap`)은 아래 3번으로 대체하는 게 근본적으로 더 나음.

## 3. 임의 업종 병합 대신 GICS 계층 + 최소 표본 기반 fallback

현재 `$scoreIndustryGroupMap`은 "업종 내 3개 미만이면 인접 업종과 합친다"를 손으로 짠 11개
매핑 표로 처리한다(예: 보험→금융·은행·증권). 이 방식의 한계:
- 새 업종이 생기거나 종목이 이동하면 매핑 표를 수동으로 갱신해야 함.
- "인접 업종"의 판단 기준이 코드 작성자의 주관("실제로 연관성이 뚜렷한 조합만 선정")이라
  일관성 검증이 어려움.

**설계 방향**: 표준 산업분류 계층(GICS 또는 KRX 업종분류의 대분류/중분류/소분류)을 도입해,
소분류 표본이 3개 미만이면 자동으로 중분류로, 그래도 부족하면 대분류로 fallback하는 알고리즘을
쓴다. 이러면 매핑 표 유지보수가 없어지고, "왜 이 업종이 저 업종과 묶였는지"가 계층 구조로
설명됨. 전제: 각 종목에 GICS(또는 KRX 표준) 코드가 있어야 함 — 현재 `index.html`의 `industry`
필드는 자유 텍스트 한글 라벨이라 매핑 테이블(종목코드 → GICS 코드) 별도 구축 필요.

## 4. OpenDART XBRL 기반 구조화 재무데이터

현재 재무데이터는 `stocks/*.html`의 "2. 기본적 분석 — 공시 원문" 섹션에 **사람이 읽는 텍스트로
이미 박제된** 값(예: `<span class="l">지배주주 순이익</span><span class="v">...</span>`)을
정규식으로 재추출하는 구조다. 이 세션에서 실측한 문제들(라벨 변형 11종, "(?!Forward)" 같은
꼼수 필요, USD 공시 종목의 단위 불일치 등)이 전부 "정형 데이터가 아니라 사람이 쓴 문구를
정규식으로 파싱"하는 데서 비롯됨.

**설계 방향**: DART Open API의 XBRL 재무제표(단일회사 전체 재무제표 API 등)를 직접 호출해
계정과목 표준코드(예: `ifrs-full_ProfitLossAttributableToOwnersOfParent`)로 값을 가져오면:
- 라벨 변형 문제가 원천적으로 사라짐(계정과목 코드는 표준화돼 있음).
- 현금흐름표(CFO/CFI/CFF)를 확보할 수 있어 1번(Value/Quality 축)의 전제 조건이 풀림.
- 연결/별도 구분이 명확해져(현재 `$script:DpEquityLabels` 우선순위 추측 방식보다) ROE 분모
  선택의 모호함이 없어짐.

**비용**: DART Open API 키 발급 및 종목별 corp_code 매핑, XBRL 파싱 로직(태그 체계가 재무제표
양식마다 달라 초기 매핑 작업 필요) — 상당한 착수 비용이 있어 P1의 다른 항목보다 선행 투자가 큼.
다만 한 번 구축하면 라벨 변형 대응 코드(현재 11개 배열 + 주석들) 상당수를 걷어낼 수 있음.

## 5. 최근 분기 재무상태표 + TTM 손익

현재 ROE/EPS성장률/재무안전성은 **연 1회(사업보고서) 재무제표만** 반영한다(vscore 산출 근거의
페이지 노출 범위는 spec.md의 "알려진 갭 2번"에 이미 문서화된 의도된 설계). 문제는 이게 최대
11개월까지 뒤처진 스냅샷일 수 있다는 것 — 예를 들어 반기 실적이 급변했어도 vscore는 그대로.

**설계 방향**: TTM(최근 12개월 rolling) 손익 = 직전 연간 실적 - 작년 동기 반기 + 올해 반기,
재무상태표는 최근 분기(1Q/반기/3Q) 기준으로 자본총계·부채총계를 갱신. 이러면 ROE/재무안전성이
분기마다 갱신되어 위 "11개월 뒤처짐" 문제가 사라짐. 전제: 4번(XBRL)이 있으면 분기 재무제표도
같은 방식으로 가져올 수 있어 훨씬 수월 — 현재처럼 페이지 텍스트에서 "1H26 지배주주 순이익"
같은 걸 다시 정규식으로 뽑는 방식은 라벨 변형 리스크가 배로 늘어남.

## 6. point-in-time 데이터와 당시 유니버스를 사용한 백테스트

vscore가 "저평가로 분류된 종목이 실제로 이후 초과수익을 냈는지"를 검증한 적이 없다(설계 당시
직관에 의존). 이걸 검증하려면:
- **point-in-time 데이터 필요**: 오늘 시점에서 "2025년 A종목 ROE"를 조회하면, 실제로는 정정공시
  이후의 최신값이 아니라 **당시(예: 2026년 3월) 공시 시점에 알 수 있었던 값**을 써야 look-ahead
  bias가 없음. 현재 파이프라인은 항상 "오늘 기준 최신" 값만 쓰므로 이 자체가 불가능 — 과거
  스냅샷을 별도로 축적해야 함.
- **당시 유니버스 필요**: KOSPI10000이 지금 106~109개 종목이지만 1년 전엔 다른 구성이었을 수
  있음 — "지금 상위 종목들"로 과거를 되짚으면 survivorship bias가 생김.

**설계 방향**: `data/fundamental_score.json`을 매일 스냅샷으로 **누적 보관**(덮어쓰지 않고
날짜별 파일 또는 타임시리즈 DB)하기 시작하는 게 첫걸음 — 지금 당장 백테스트를 못 해도, 앞으로
쌓이는 데이터가 미래의 P2(백테스트) 작업의 원재료가 됨. 이번 P0에서 `calculated_at` 필드를
넣어둔 것도 이 목적과 연결됨(과거 스냅샷을 구분할 수 있는 최소한의 장치).

## 7. 기술점수와 단순 합산하지 않고 분포 표준화 후 결합

spec.md "알려진 갭 3번"에 이미 문서화된 항목을 P1 범위로 재확인: 현재 홈페이지 "총점"은
`vscore + technical_score`(200점 만점 단순 합)다. 두 점수의 분포 특성이 다르면(vscore는
percentile 기반이라 이론상 균등분포에 가깝고, technical_score는 조건 충족형이라 특정 구간에
몰릴 수 있음) 단순 합산은 한쪽이 총점을 좌우하는 왜곡을 만들 수 있다.

**설계 방향**: 두 점수를 각각 z-score(또는 그날의 유니버스 내 rank-based normal score)로
표준화한 뒤 결합. 예: `total = 0.5 * zscore(vscore) + 0.5 * zscore(technical_score)`, 다시
0~100 스케일로 매핑. 전제: 표준화 기준 모집단(그날 점수가 있는 전 종목)을 정의해야 하고,
매일 분포가 바뀌므로 "어제 총점 72"와 "오늘 총점 72"가 절대적으로 비교 가능하지 않다는 걸
사용자에게 설명하는 UI 문구가 필요.

## 우선순위 제안 (다음 세션 참고용)

착수 난이도와 현재 P0 대비 파급력을 감안하면:
1. **7번(총점 표준화)** — 데이터 추가 없이 계산식만 바꾸는 가장 저비용 항목, 가장 먼저 시도 가능.
2. **3번(GICS 계층)** — 매핑 테이블 하나 구축하면 되고, 4/1/5번의 전제 조건은 아님.
6. **4번(XBRL)** — 착수 비용은 크지만 1/5번의 선행 조건이라, 이걸 먼저 해야 나머지가 열림.
이후 1번(가치/품질/성장 분리) → 5번(TTM/분기 갱신) → 2번(업종별 모델) → 6번(백테스트) 순으로
파생 가능. 2번은 스코어링 세분화 작업이라 1번 이후가 자연스럽고, 6번은 데이터가 누적돼야
의미가 있어 가장 나중.
